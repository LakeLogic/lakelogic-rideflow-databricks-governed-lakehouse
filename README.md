# rideflow_databricks_lakehouse

A governed medallion lakehouse on Databricks, generated by LakeLogic. Every table is defined by
a data contract; the jobs run those contracts and record what passed, what was quarantined and why.
Edit the contracts, not the notebooks.

## Quickstart

### Before you start

- The Databricks CLI, signed in to the workspace (`databricks auth login`).
- Permission to create catalogs, or catalogs already created with the names above.
- Secrets (`databricks secrets put-secret <scope> <name>`):
- `dev`: secret `eventhubs-rideflow` in scope `rideflow` — Source credential (eventhubs_rideflow_connection_string), required.

### Deploy and run

```bash
cd platform/databricks
./deploy.sh dev          # or deploy.ps1 on Windows
```

Then run `pl_admin_setup` once: it creates the schemas, volumes and run-log tables. Safe to re-run.
Run `pl_data_00_mesh_orchestrator` to run every system in dependency order, or run one system's job on its own.

`pl_test_synthetic_seed` writes synthetic landing files from the contract schemas (no production rows read), so the pipeline can run before real data arrives.

### Check the result

Each run writes a row per contract to `lakelogic_run_log` in the domain catalog's `lakelogic` schema:
rows read, written and quarantined. Rejected rows land in `quarantine_<table>` with the rule that
failed them.

## Where things are

- `contracts/<domain>/_domain.yaml` — domain defaults.
- `contracts/<domain>/<system>/_system.yaml` — the system registry: storage, environments, contracts.
- `contracts/<domain>/<system>/contracts/<layer>/<dataset>.yaml` — the data contracts.
- `platform/databricks/databricks.yml` — the Asset Bundle, one target per environment.
- `platform/databricks/resources/` — jobs: `data/` (one per system), `admin/`, `monitor/`, `privacy/`, `test/`.
- `platform/databricks/notebooks/` — the drivers the jobs run.
- `platform/databricks/tests/` — structural tests; `.github/workflows/validate.yml` runs them with contract validation.

## Operate

- `pl_monitor_slo` — service levels, daily.
- `pl_admin_maintenance` — OPTIMIZE and VACUUM, weekly (dry run by default).
- `pl_privacy_erasure` — erasure requests (dry run by default); `pl_privacy_retention` — retention, daily.
